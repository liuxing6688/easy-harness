## 场景 1: 新建项目（Greenfield）

### 背景
从零创建一个新项目，比如待办事项应用

### 适用模式
✅ **full** (完整流程)

### 完整步骤

#### 第 1 步：启动流程
```
在 Claude Code 中输入：

"使用 Harness Engineering 规约，按 full 模式创建一个待办事项管理应用，
技术栈：React + TypeScript + Node.js + SQLite"
```

#### 第 2 步：PM 确认
AI（项目经理）会问：
- 确认工作流模式：`full`？
- 确认技术栈：React + Node.js + SQLite？

**你的回答**：是的，确认

#### 第 3 步：需求澄清（RA）
需求分析师会用苏格拉底式提问澄清：
- 用户权限管理？（多用户 or 单用户）
- 任务字段？（标题、描述、优先级、截止日期？）
- 部署方式？（本地 or 云端）

**典型对话**：
```
RA: 这个应用是给单个用户用，还是支持多用户？
你: 单用户本地使用

RA: 任务需要哪些属性？标题、描述、截止日期、优先级？
你: 标题、描述、完成状态就够了，暂时不要优先级

RA: 需要什么持久化方案？
你: SQLite 本地数据库
```

#### 第 4 步：架构设计（SA）
系统架构师会产出 `docs/detail-design-spec.md`：
- 技术栈确认
- 目录结构
- 数据模型（todos 表）
- API 接口设计（GET/POST/PUT/DELETE /api/todos）
- 前端组件结构

**你需要做什么**：审阅设计，如有问题提出

#### 第 5 步：设计审核（RR）
需求评审专家会检查 12 个维度：
- 需求覆盖
- 技术可行性
- 安全性
- 性能
- 可测试性
- ...

**通常自动通过**，除非设计有明显问题

#### 第 6 步：开发实现（DE）
开发工程师会：
1. 初始化项目（`npm create vite@latest`）
2. 安装依赖
3. 实现后端 API
4. 实现前端组件
5. 连接前后端
6. 通过 **R15 (Lint)** 和 **R16 (静态扫描)** 门禁

**你需要做什么**：等待完成（约 1-2 小时）

#### 第 7 步：质量审查（QE）
质量工程师会：
- 检查代码质量
- 生成 `docs/quality-report.md`
- 评分（目标 ≥ 4/5）

#### 第 8 步：测试（TE）
测试工程师会分两轮：

**批次测试**：
- 集成测试（后端 API）
- 通过 **R32 (启动冒烟)**

**最终测试**：
- E2E 测试（真实浏览器）
- 通过 **R34 (执行证明)**
- 生成 `docs/test-report.md`

#### 完成标志
```
✅ docs/process/process.md 显示：当前阶段: 已完成
✅ docs/quality-report.md 质量评分 ≥ 4/5
✅ docs/test-report.md 所有测试通过
✅ 应用可正常运行
```

### 预计耗时
**3-4 天**（AI 执行时间：4-6 小时）

## 场景 2: 修复生产 Bug（Hotfix）

### 背景
生产环境发现：用户登录后头像显示为默认图标，而不是用户上传的头像

### 适用模式
✅ **hotfix** (快速修复)

### 前置条件
- ✅ 已有 `docs/detail-design-spec.md`
- ✅ 是缺陷修复，不是新功能

### 完整步骤

#### 第 1 步：启动流程
```
"使用 Harness Engineering 规约，按 hotfix 模式修复用户头像显示错误问题"
```

#### 第 2 步：PM 确认
AI 会问：
- 确认这是缺陷修复？
- 已有设计文档？
- 不涉及架构变更？

**你的回答**：是的，确认

PM 会完成 **R9 最小影响澄清**：
- 受影响用户：所有已登录用户
- 既有行为：应该显示用户头像，实际显示默认图标
- 回滚条件：如果修复后头像完全不显示
- P0 判断：是（影响用户体验）

#### 第 3 步：直接开发（DE）
跳过 RA 和 SA，开发工程师直接：
1. 定位问题（前端从 API 读取 `avatar` 字段，后端返回的是 `avatarUrl`）
2. 修复代码（统一为 `avatarUrl`）
3. 通过 R15 (Lint) + R16 (静态扫描)

#### 第 4 步：质量审查（QE）
快速审查修复

#### 第 5 步：单次测试（TE）
**hotfix 特权**：不分批次/最终，只做一次集成测试 + E2E
- R32 (启动冒烟)
- R34 (执行证明)
- R11 折叠：单次通道覆盖所有

#### 完成标志
```
✅ 头像正确显示
✅ 测试通过
✅ 流程记录在 docs/process/process.md
```

### 预计耗时
**4 小时**（AI 执行时间：30 分钟）

## 场景 3: 添加新功能（Feature）

### 背景
在已有的待办应用上，添加"任务分类"功能（不改已有数据表结构）

### 适用模式
❌ ~~hotfix~~ (不是缺陷)  
❌ ~~single-task~~ (需要改 Schema)  
✅ **full** (涉及数据模型变更)

### 为什么不能用 single-task？
因为需要新增 `categories` 表和 `category_id` 外键，这是 **Schema 变更**

### 完整步骤

类似场景 1，但：
1. RA 会基于已有需求文档，增量澄清
2. SA 会更新 `docs/detail-design-spec.md`，添加新章节
3. 其余流程完整

### 预计耗时
**3-4 天**（AI 执行时间：3-4 小时）

## 场景 4: 功能增量迭代（Single-Task）

### 背景
在已有应用上，添加"导出 CSV"功能（不改数据库，不新增 API）

### 适用模式
✅ **single-task** (增量迭代)

### 前置条件
- ✅ 已有 `docs/detail-design-spec.md`
- ✅ 不改 Schema
- ✅ 不新增对外 API（只在前端添加导出按钮）

### 完整步骤

#### 第 1 步：启动流程
```
"使用 Harness Engineering 规约，按 single-task 模式添加任务列表导出为 CSV 功能"
```

#### 第 2 步：PM 确认并声明增量范围
PM 会在 `docs/process/process.md` 写入：

```markdown
## 增量范围

| 影响面 | 是否涉及 | 说明 |
|--------|---------|------|
| 新增/变更对外接口 | 否 | 仅前端功能，不新增 API |
| 数据模型/Schema 变更 | 否 | 不改数据库 |
| 新增交互面 | 否 | 只在现有页面加导出按钮 |
| 影响的既有行为 | 否 | 不影响既有任务增删改查 |
```

#### 第 3 步：完整角色链
RA → SA → RR → DE → QE → TE（一个都不省）

**关键区别**：
- ✅ 保留所有验证（R15/R16/R32/R34）
- ✅ 保留设计审核（R18）
- ✅ 豁免技术选型确认（R26，沿用已有技术栈）
- ✅ **测试只做一轮**（不分批次/最终）

#### 第 4 步：单轮测试
TE 执行 `--scope=final` 语义的单轮测试：
- 集成测试
- E2E 测试
- 启动冒烟
- 执行证明

#### 完成标志
```
✅ 导出功能正常工作
✅ 所有门禁通过
✅ 测试通过（单轮）
```

### 预计耗时
**2.5 天**（AI 执行时间：2-3 小时）

## 场景 5: 更新文档（Docs-Only）

### 背景
修正 README.md 中的安装说明错误

### 适用模式
✅ **docs-only** (仅文档)

### 完整步骤

#### 第 1 步：启动流程
```
"使用 Harness Engineering 规约，按 docs-only 模式更新 README 的安装说明"
```

#### 第 2 步：PM 确认
- 确认只改 `docs/**/*.md`？
- 不涉及代码？

#### 第 3 步：直接修改
PM 直接修改文档，无需其他角色

#### 注意
**Hook 会拒绝写源码**：如果尝试改 `.js/.ts` 文件，会被阻止

### 预计耗时
**10 分钟**

## 场景 6: 重构代码

### 背景
重构登录模块，提取公共函数，但不改功能

### 适用模式
✅ **hotfix** (如果已有设计且只是代码优化)  
或  
✅ **full** (如果改动较大)

### 决策逻辑
```
重构改变外部行为？
├─ 不改 → hotfix（代码级优化）
└─ 改变 → full（需要重新设计）
```

### 完整步骤
同场景 2（hotfix）或场景 1（full）

## 场景 7: 数据库 Schema 变更

### 背景
给 `users` 表添加 `email` 字段

### 适用模式
✅ **full**（强制，Schema 变更禁止 single-task）

### 为什么必须 full？
数据模型变更涉及：
- 数据迁移脚本
- 兼容性测试
- 回滚方案

需要完整测试覆盖（批次 + 最终）

### 完整步骤
1. 启动 `full` 模式
2. SA 设计迁移方案（添加字段、默认值、索引）
3. DE 实现迁移脚本
4. TE 测试数据迁移（旧数据兼容性）

## 场景 10: 处理门禁失败

### 背景
开发完成后，R16 (静态扫描) 门禁失败：代码重复率 8% (阈值 5%)

### 诊断步骤

#### 第 1 步：查看详细报告
```bash
node .claude/scripts/static-scan-run.mjs
```

输出会显示：
```
❌ 重复率: 8.3% (阈值: 5%)
重复代码位置:
- src/utils/auth.js:10-25 与 src/utils/session.js:15-30
```

#### 第 2 步：分析原因
两个文件有相同的登录验证逻辑

#### 第 3 步：修复
告诉 AI：
```
"R16 门禁失败，代码重复率 8%，请重构 auth.js 和 session.js 的重复逻辑"
```

AI（DE 角色）会：
1. 提取公共函数到 `src/utils/validation.js`
2. 更新两个文件引用公共函数
3. 重新运行 R16

#### 第 4 步：验证
```bash
node .claude/scripts/static-scan-run.mjs
```

输出：
```
✅ 重复率: 3.2% (阈值: 5%)
✅ 无安全漏洞
```

### 常见门禁失败及解决

| 门禁 | 失败原因 | 解决方法 |
|------|---------|---------|
| R15 | 代码风格不一致 | 运行 `eslint --fix` 自动修复 |
| R16 | 代码重复率 > 5% | 重构提取公共函数 |
| R16 | 安全漏洞 | 升级依赖或修复代码 |
| R32 | 应用启动失败 | 检查依赖和配置 |
| R32 | 强杀重启失败 | 检查进程清理逻辑 |
| R34 | 测试未真实运行 | 确保 E2E 测试脚本正确 |

## 快速参考：场景 → 模式映射

| 场景 | 推荐模式 | 原因 |
|------|---------|------|
| 新建项目 | `full` | 需要完整设计 |
| 修 Bug（已有设计） | `hotfix` | 快速修复 |
| 修 Bug（无设计） | `full` | 需要补设计 |
| 加功能（改 Schema） | `full` | Schema 变更必须 full |
| 加功能（不改 Schema，有设计） | `single-task` | 增量迭代 |
| 加功能（无设计） | `full` | 需要设计 |
| 只改文档 | `docs-only` | 最轻量 |
| 重构（不改行为） | `hotfix` | 代码优化 |
| 重构（改行为） | `full` | 需要重新设计 |
| API 变更 | `full` | 影响对外接口 |
| 只加测试 | `single-task` | 增量测试 |
