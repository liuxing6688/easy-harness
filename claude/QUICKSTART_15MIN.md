## 📋 三步决策：选择你的工作流模式

回答 3 个问题，找到适合的模式：

```
问题 1: 这是什么类型的工作？
├─ 🆕 新建项目/新功能 → 问题 2
├─ 🐛 修复 Bug → 问题 2  
├─ 📝 只改文档 → ✅ 使用 docs-only 模式
└─ ➕ 小功能增量（已有设计）→ 问题 3

问题 2: 已有设计文档吗？
├─ ✅ 有 + 是修 Bug → ✅ 使用 hotfix 模式（4 小时）
├─ ✅ 有 + 是新功能 → 问题 3
└─ ❌ 没有 → ✅ 使用 full 模式（4 天）

问题 3: 会改数据库结构/API Schema 吗？
├─ 会 → ✅ 使用 full 模式
└─ 不会 → ✅ 使用 single-task 模式（2.5 天）
```

### 模式速查表

| 模式 | 适用场景 | 耗时 | 关键特点 |
|------|---------|------|---------|
| **full** | 新项目、大功能、改 Schema | 4 天 | 完整流程：需求→架构→审核→开发→测试 |
| **hotfix** | 紧急修 Bug（已有设计） | 4 小时 | 跳过需求/架构，单次测试 |
| **single-task** | 功能增量（已有设计，不改 Schema） | 2.5 天 | 保留所有验证，单轮测试 |
| **docs-only** | 仅改文档 | 2 小时 | 只改 `docs/**/*.md`，禁止写代码 |

## 👥 7 个角色协作（自动）

你只需提出目标，AI 自动编排这些角色：

```
用户提出目标
    ↓
📋 PM (项目经理) - 接收目标，确认模式，编排流程
    ↓
📝 RA (需求分析师) - 澄清需求细节（苏格拉底式提问）
    ↓
🏗️ SA (系统架构师) - 设计技术方案
    ↓
🔍 RR (需求评审专家) - 审核设计（12 维度检查）
    ↓
💻 DE (开发工程师) - 实现代码
    ↓
✅ QE (质量工程师) - 代码审查、质量报告
    ↓
🧪 TE (测试工程师) - 执行测试、生成报告
```

**轻量模式简化**：
- `hotfix`: PM → DE → QE → TE（单次）
- `docs-only`: PM 直接改文档
- `single-task`: 完整角色链，单轮测试

## 🔒 4 个自动质量门禁

无需手动操作，AI 自动执行并验证：

| 门禁 | 作用 | 何时触发 |
|------|------|---------|
| **R15: Lint** | 代码风格检查 | 每次代码提交前 |
| **R16: 静态扫描** | 安全漏洞 + 代码重复率 < 5% | 开发完成后 |
| **R32: 启动冒烟** | 应用能否正常启动 + 强杀重启 | 测试阶段 |
| **R34: 执行证明** | 测试真实运行证明 | 测试报告提交时 |

**不通过会怎样？** AI 会自动修复并重试，确保质量。

## ⚠️ 3 个常见错误

### 错误 1：没有确认模式就开始

❌ **错误做法**:
```
"帮我加个导出功能"
```

✅ **正确做法**:
```
"使用 Harness Engineering 规约，按 single-task 模式添加导出功能"
```

**原因**: 未指定模式会默认走 full 模式（最重流程）

---

### 错误 2：hotfix 模式用于新功能

❌ **错误做法**:
```
"按 hotfix 模式添加用户注册功能"  （hotfix 只能修 Bug）
```

✅ **正确做法**:
```
"按 single-task 模式添加用户注册功能"  （新功能用 single-task 或 full）
```

**原因**: hotfix 要求已有设计且仅修复缺陷

---

### 错误 3：改 Schema 时用 single-task

❌ **错误做法**:
```
"按 single-task 模式给用户表加个 email 字段"  （改数据库 Schema）
```

✅ **正确做法**:
```
"按 full 模式给用户表加个 email 字段"  （Schema 变更必须 full）
```

**原因**: 数据模型变更需要完整测试覆盖

## 💡 核心理念（理解这个就够了）

1. **角色分离**: 每个角色只做自己的事，不越界
2. **质量门禁**: 关键操作自动验证，确保质量
3. **流程留痕**: 所有决策记录在 `process.md`，可追溯
4. **模式分级**: 根据改动大小选择合适流程，避免过重
